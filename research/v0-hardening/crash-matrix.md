## What the runtime KNOWS, DOESN'T KNOW, and DOES — by crash point

The brief's real question is not "does it restart?" but "what does the runtime know, what does it
not know, and what does it safely do?" Grouped by that:

### Group A — crash BEFORE any side effect
`after:model.requested` · `after:model.responded` · `after:tool.requested` · `after:tool.authorized`

- **Knows:** the last durable event; no `tool.started` exists.
- **Doesn't know:** whether the model call it issued was billed (the response never landed).
- **Does:** nothing special. The projection has no pending tool call, so the loop simply continues
  from the last durable state. The model is re-asked.
- **Cost of the crash:** one wasted model call. No world effect is at risk.
- **Observed:** 0 orphans, resume completes, world matches golden.

### Group B — crash in the effect window (**the hard case**)
`after:tool.started` · `after:tool.effect`

These two bracket the exact window ADR-002 exists for. The durable log is *identical* in both
(`9 tool.started`) — the runtime cannot tell them apart from the log alone.

- **Knows:** a tool was authorized and started, with these arguments. No terminal event.
- **Doesn't know:** whether the effect landed.
- **Does:** calls `recovery(args)`, then `verify()`. Observed, from the same log state:

```
after:tool.started  ->  write SAFE_RETRY -> reissue (verify: not-applied)
after:tool.effect   ->  write SAFE_RETRY -> skip    (verify: applied)
```

**This is the core result of the whole phase.** Identical durable state, opposite decisions,
resolved by probing the world rather than guessing. Both paths converge on the golden world state.

When no `verify()` is available and the class is `UNSAFE`, the run **pauses and asks a human**
(`tests/recovery/recovery.test.mjs`, "UNSAFE orphan pauses the run"). It never guesses.

### Group C — crash AFTER the terminal event
`after:tool.succeeded` · `before:terminal`

- **Knows:** everything. The tool result is durable.
- **Doesn't know:** nothing relevant.
- **Does:** resumes from the next step. No recovery machinery engages.

## Per-crash-point answers to the required questions

| question | answer |
|---|---|
| What state was persisted? | Every event committed before the kill. `synchronous=FULL` means a committed event survives power loss. Verified: `tests/unit/event-store.test.mjs` "committed event survived the kill". |
| What gets retried? | The model call (always safe — no world effect). Tool calls only when `recovery()` says `reissue`. |
| What gets duplicated? | **Nothing, in 16/16 scenarios.** Measured by comparing the final world to a golden no-crash run, not by counting events. |
| What is idempotent? | `read`, `grep` (READ_ONLY); `write` (SAFE_RETRY, whole-content); `edit` (SELF_VERIFYING, rejects its own replay); `bash` **only for known-safe arguments**. |
| What is lost? | At most one in-flight model call. Tool effects are never lost — they either landed (and are detected) or did not (and are re-issued). |
| Can execution resume? | Yes, in every scenario, by a **different process**. |
| Can the system prove what happened? | Yes. `tool.recovery_decided` records class, decision, and the `verify()` verdict. `harness explain` renders it. |
| Can the exact state be recreated? | Yes — `replay()` folds the log with zero model calls. |
| Is the failure mode explicit or silent? | Explicit. Every recovery emits `tool.recovery_decided` **and** a `degraded` event, and lease loss emits `run.lease_lost`. |

## Limits of this matrix — stated plainly

1. **The model is a scripted HTTP server, not an LLM.** Crash behaviour of the *runtime* is
   measured; how a real model reacts to a repaired transcript is not.
2. **8 crash points, not 15.** The brief lists 15; several (`before/after snapshot`,
   `before/after lease renewal`, `before human request`) are not distinct durable states in this
   implementation — snapshots are derived data (losing one costs a slower replay, nothing else) and
   lease renewal is idempotent. `after:human.requested` is covered separately in
   `tests/recovery/recovery.test.mjs` and by the CLI walkthrough. Rather than pad the matrix with
   points that cannot fail distinctly, they are named here.
3. **Single crash per run.** Repeated crashes during recovery are untested.
4. **Local filesystem only.** A crash mid-write to a network filesystem may leave a torn file that
   `verify()` would misreport as applied.
5. **One tool class per crash point.** `write` (SAFE_RETRY) and `grep` (READ_ONLY) were exercised;
   an `UNSAFE` orphan is covered in the recovery suite, not here.
